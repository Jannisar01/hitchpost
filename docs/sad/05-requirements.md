What Hitchpost must do and how well, from what exists today (Phase 1 plus the audit fixes) through production. Each requirement has an ID, a phase, a status, a MoSCoW priority and a source, and traces to a use case, a design section, a verification method and a test case.

## 1. Purpose and scope

**Product.** Hitchpost is a network of agent lines between users: person to person and person to business. Every person or business gets an agent line (an identity plus an A2A agent card), a contact list of other agent lines, a public directory for businesses, verification and reputation, and a human approval gate in front of every commitment. Barbers are the beachhead vertical that proves it ([ADR 0008](../decisions/0008-first-vertical-barbers.md)), not the product.

**In scope:** asking another agent line for availability, a human approval gate, booking and changing bookings, person-to-person time agreement between two people's agents (UC-11), a public directory of business agent lines, a client app with agent lines as contacts, outcomes and ratings from verified interactions, and the operator tools that keep the network safe.

**Out of scope until Later:** payments and deposits, a natural-language front end, federation between directories, manual shop approval of each booking (designed in FR-GATE-05, not shipped in the pilot), auto-accept rules by customer history, EU expansion. See [01. Vision and scope](01-vision-and-scope.md).

**Jurisdiction.** The pilot runs in the United States (Texas, USD, America/Chicago). Legal requirements are tracked in [35 Legal, compliance and governance](35-legal-compliance-and-governance.md).

**Values.** Numeric values (holds, timeouts, limits, retention) are not restated here as free numbers. Each is a normative parameter `P-nn` defined once in the parameter register of [00 Document control](00-document-control.md). Where a value appears in this document it is followed by its P-ID, and the register wins if they ever differ.

## 2. Definitions

| Term                 | Meaning                                                                                                                                                                         |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Agent line           | A person's or business's identity on Hitchpost: an A2A agent with a card, reachable by other agent lines.                                                                       |
| Agent                | Software that acts for one party (a person or a business) and speaks A2A.                                                                                                       |
| Agent card           | The A2A document at `/.well-known/agent-card.json` that says who an agent is and how to reach it.                                                                               |
| Offer                | A business agent's proposal of one slot: `serviceId`, service name, start, duration, price, currency, disclosure fields, `offerId`, `issuedAt`, `expiresAt`.                    |
| Hold                 | The slot an unexpired offer keeps out of other offers (P-01).                                                                                                                   |
| Standing approval    | The business's opening hours count as its yes to any valid booking inside them. The only business-side approval mode in the pilot.                                              |
| Approval             | A person's explicit yes to one specific offer.                                                                                                                                  |
| Commitment           | Any action that spends a person's money, books their time or shares their personal data.                                                                                        |
| Verified interaction | An interaction with a logged offer and a matching logged decision on both sides, ending in a booking that reached Completed or NoShow.                                          |
| Honored booking      | A booking that reached Completed. The north star counts these. Outcomes are never billed.                                                                                       |
| Inbound data         | Anything received from another agent. Always untrusted.                                                                                                                         |
| Install key          | A random 128-bit key generated per personal-agent install, sent in the `Hitchpost-Install-Key` header, used to key hold caps and rate limits before agent authentication.       |

## 3. Constraints and assumptions

**Constraints**

- Agent-to-agent messaging uses A2A v1.0 through the official SDK ([ADR 0003](../decisions/0003-build-on-a2a-and-mcp.md)).
- TypeScript on Node 24, one monorepo ([ADR 0002](../decisions/0002-typescript-monorepo.md)); service boundaries in [26 Service architecture](26-service-architecture.md) and [ADR 0019](../decisions/0019-service-architecture.md).
- Messages between agents are typed data parts, not free text ([ADR 0010](../decisions/0010-typed-data-parts-before-llm.md)). Phases 1 to 3 are rule-based; nothing is marketed as AI that isn't.
- MIT licensed, built in the open ([ADR 0004](../decisions/0004-mit-open-source.md)).
- No payments or deposits in v1 (R-09 in [03](03-business-case.md)).
- Times on the wire are UTC. Before Phase 6 the book is UTC only and every booking is a demonstration; no real customer booking happens before Phase 6, when per-business IANA zones arrive (FR-BOOK-05, ADR 0018).
- The contract version is declared once, as an `AgentCapabilities.extensions` entry on the agent card (uri `https://hitchpost.dev/ext/contract/v1`, `required: true`), and messages list that uri in their `extensions`. The A2A `AgentCard` has no metadata field to carry it ([13](13-interfaces.md)).
- The A2A SDK stops draining a task's events at `INPUT_REQUIRED` (`@a2a-js/sdk` 1.3 `server/index.js:2181`), and A2A defines that state as "the caller must reply". It is never used to wait for a business owner (FR-GATE-05).

**Assumptions:** the business assumptions this specification rests on are tracked with their tests in [03. Business case](03-business-case.md) and the consolidated [33 RAID log](33-raid-log.md). If one fails, the requirements that depend on it are revisited, not built anyway.

| Assumption                                                     | Requirements that depend on it                                |
| -------------------------------------------------------------- | ------------------------------------------------------------- |
| A-01 people will approve agent offers                          | FR-GATE-01 to FR-GATE-05, FR-BOOK-01 to FR-BOOK-17, FR-APP-07 |
| A-02, A-03 businesses list; their tools allow reads and writes | FR-DIR-01, FR-BOOK-06                                         |
| A-04 agent booking is faster                                   | NFR-PERF-01, the whole Phase 2 flow                           |
| A-06 verified reviews are trusted more                         | FR-RATE-01 to FR-RATE-06, FR-DIR-05                           |
| A-08 the built-in personal agent is enough at launch           | FR-APP-03, FR-APP-07                                          |

## 5. User stories for the next phases

Phase 2 and Phase 3 stories are here. The full backlog with every epic, story and acceptance criterion is in [24 Product requirements document](24-product-requirements-document.md).

### Phase 2

**FR-GATE-01, FR-GATE-02.** As Dana, I want to approve one specific offer, so that my agent can never book something I didn't see.

- **Given** my agent received a valid offer for a haircut on Thursday at 17:30 for 30.00 USD, **when** I approve it, **then** my agent sends a `booking_request` for that `offerId` only, and the approval is recorded in my audit log.
- **Given** I approved offer A, **when** any code tries to book offer B with that approval, **then** it is refused and nothing is sent.
- **Given** the offer is within P-09 of its deadline or past it, **when** I approve it, **then** my agent tells me it expired and asks the business agent for a fresh offer.

**FR-BOOK-01, FR-BOOK-02, FR-BOOK-07, FR-GATE-05.** As Marcus, I want offers to hold the slot briefly and bookings to be decided once inside my opening hours, so that two customers are never given the same chair and I don't have to answer anything.

- **Given** the business agent offered 17:30 to Dana, **when** another agent asks for the same window before the offer expires, **then** 17:30 is not offered.
- **Given** a `booking_request` with an unknown or expired `offerId`, **when** it arrives, **then** the business agent answers `booking_rejected` (`unknown_offer` or `expired`) and its book is unchanged.
- **Given** two `booking_request`s for the same offer arrive together, **when** both are processed, **then** exactly one booking exists and the other send gets the same result with `duplicateOf`.
- **Given** a valid `booking_request` inside opening hours, **when** it arrives, **then** it is confirmed at once with no action from me.

**FR-BOOK-08, FR-BOOK-09, FR-MSG-13.** As Marcus, I don't want strangers to lock up my chairs with offers they never take.

- **Given** Dana declines an offer, **when** her agent sends `offer_declined`, **then** the slot is offered again at once.
- **Given** one install already has P-07 open holds, **when** it asks again, **then** it gets `rejected` reason `hold_cap` and no new hold.
- **Given** an agent resends the same `availability_request` (same `messageId`), **when** it arrives, **then** it gets the original reply and no second hold.

**FR-BOOK-14, FR-BOOK-17.** As Marcus, I want to know who is coming; as Dana, I want to know what I'm agreeing to.

- **Given** Dana approved an offer, **when** the `booking_request` arrives, **then** it carries her display name and verified phone, which only Main Street Barbers can see.
- **Given** an offer, **when** Dana reviews it, **then** it shows the business's legal name, the total with a tax statement, the cancellation terms and the business phone.

**FR-GATE-03, FR-MSG-11.** As Dana or Marcus, I want a record of what my agent proposed and what was decided, so that I can check what happened if something goes wrong.

- **Given** a completed booking, **when** I read my audit log, **then** it shows the offer, my decision with a timestamp, the booking request and the result, in order, each with the shared `contextId`, `taskId`, `offerId` and `messageId`, with no entries changed or removed.

**FR-BOOK-03, FR-BOOK-10, FR-BOOK-11.** As Dana, I want to cancel or move my booking through my agent, so that I don't have to call the shop.

- **Given** a confirmed booking, **when** I cancel it with its `bookingToken`, **then** the business's book frees the slot, both audit logs record the cancellation, and the slot can be offered again.
- **Given** the business has a cutoff and I'm inside it, **when** I cancel, **then** the Task ends REJECTED with `cancel_rejected` reason `cutoff` and my booking stands.
- **Given** I reschedule and the new slot is taken before I approve, **when** the booking fails, **then** my original booking is unchanged.
- **Given** my agent lost the response to a `booking_request`, **when** it resends without a `taskId`, **then** it gets the same `booking_confirmed` with `duplicateOf` and the book still holds one booking.

**FR-BOOK-15, FR-ADMIN-03.** As Marcus, if I'm out sick I need my customers told; as the operator, I need to stop everything fast.

- **Given** Marcus asks the operator to cancel tomorrow's bookings, **when** the operator uses the relay tool, **then** each customer is contacted and both audit logs record `booking_cancelled_by_business`.
- **Given** a SEV1 incident, **when** the operator runs the pause command, **then** every listing is paused and shows its business phone.

### Phase 3

**FR-DIR-01.** As Marcus, I want to list my shop's agent line, so that customers' agents can find me.

- **Given** I submit my agent card URL and place the verification token on that origin (or its DNS), **when** verification runs, **then** the listing goes live marked as verified.
- **Given** I can't prove control, **when** I submit, **then** the listing is not published.

**FR-DIR-02.** As Dana, I want to find a barber near me who does fades, so that my agent can ask them for a slot.

- **Given** listings exist, **when** I search for "fade" near my area, **then** I get matching verified listings with their agent card links, nearest first.

**FR-DIR-03, FR-DIR-06.** As Dana, I want my agent to talk only to the business I picked, so that a listing can't redirect me somewhere else or pass itself off as another shop.

- **Given** a listing at `https://shop.example`, **when** its card's interface URL points at another origin, **then** my agent refuses to send it anything and the directory flags the listing.
- **Given** a new listing named "Main Street Barbers" written with look-alike letters, **when** it is submitted, **then** it is held for operator review.
