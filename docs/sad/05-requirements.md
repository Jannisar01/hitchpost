What Hitchpost must do and how well, from what exists today (Phase 1 plus the audit fixes) through production. Each requirement has an ID, a phase, a status and a source, and traces to a use case, a design section, a verification method and a test case.

## 1. Purpose and scope

**In scope:** agent-to-agent appointment booking for one vertical (barbers, [ADR 0008](../decisions/0008-first-vertical-barbers.md)): asking for availability, a human approval gate, booking and changing bookings, a public directory of business agents, a client app with agents as contacts, and ratings from verified interactions.

**Out of scope until Later:** payments and deposits, verticals other than appointment booking, a natural-language front end, federation between directories, and shop-side cancellation of a confirmed booking over the protocol (in v1 the shop contacts the customer out of band). See [01. Vision and scope](01-vision-and-scope.md).

**Values.** Numeric values (holds, timeouts, limits, retention) are not restated here as free numbers. Each is a normative parameter `P-nn` defined once in the parameter register of [00 Document control](00-document-control.md). Where a value appears in this document it is followed by its P-ID, and the register wins if they ever differ.

## 2. Definitions

| Term                 | Meaning                                                                                                                                |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Agent                | Software that acts for one party (a person or a business) and speaks A2A.                                                              |
| Agent card           | The A2A document at `/.well-known/agent-card.json` that says who an agent is and how to reach it.                                      |
| Offer                | A barber agent's proposal of one slot: service, start, duration, price, currency, `offerId`, `issuedAt`, `expiresAt`.                  |
| Hold                 | The slot an unexpired offer keeps out of other offers (P-01).                                                                          |
| Reserved             | The state of an offer once a `booking_request` for it has been accepted while the shop decides (P-02).                                 |
| Approval             | A person's explicit yes to one specific offer.                                                                                         |
| Commitment           | Any action that spends a person's money, books their time or shares their personal data.                                               |
| Verified interaction | An interaction with a logged offer and a matching logged decision on both sides, ending in a booking that reached Completed or NoShow. |
| Honored booking      | A booking that reached Completed. The north star counts these.                                                                         |
| Inbound data         | Anything received from another agent. Always untrusted.                                                                                |
| Verification method  | **T** test, **A** analysis, **I** inspection, **D** demonstration (ISO/IEC/IEEE 29148 §6.5).                                           |

## 3. Constraints and assumptions

**Constraints**

- Agent-to-agent messaging uses A2A v1.0 through the official SDK ([ADR 0003](../decisions/0003-build-on-a2a-and-mcp.md)).
- TypeScript on Node 24, one monorepo ([ADR 0002](../decisions/0002-typescript-monorepo.md)).
- Messages between agents are typed data parts, not free text ([ADR 0010](../decisions/0010-typed-data-parts-before-llm.md)).
- MIT licensed, built in the open ([ADR 0004](../decisions/0004-mit-open-source.md)).
- No payments or deposits in v1 (R-09 in [03](03-business-case.md)).
- Times on the wire are UTC. Before Phase 6 the book is UTC only and every booking is a demonstration; no real customer booking happens before Phase 6, when per-business IANA time zones arrive (FR-BOOK-05, ADR 0018).
- The contract version is declared once, as an `AgentCapabilities.extensions` entry on the agent card (uri `https://hitchpost.dev/ext/contract/v1`, `required: true`), and messages list that uri in their `extensions`. The A2A `AgentCard` has no metadata field to carry it ([13](13-interfaces.md)).
- The A2A SDK stops draining a task's events at `INPUT_REQUIRED` (`@a2a-js/sdk` 1.3 `server/index.js`), and A2A defines that state as "the caller must reply". It is therefore never used to wait for a shop owner (FR-GATE-05).

**Assumptions:** the business assumptions this specification rests on are tracked with their tests in [03. Business case](03-business-case.md). If one fails, the requirements that depend on it are revisited, not built anyway.

| Assumption                                                  | Requirements that depend on it                     |
| ----------------------------------------------------------- | -------------------------------------------------- |
| A-01 people will approve agent offers                       | FR-GATE-01 to FR-GATE-05, FR-BOOK-01 to FR-BOOK-11 |
| A-02, A-03 barbers list; their tools allow reads and writes | FR-DIR-01, FR-BOOK-06                              |
| A-04 agent booking is faster                                | NFR-PERF-01, the whole Phase 2 flow                |
| A-06 verified reviews are trusted more                      | FR-RATE-01 to FR-RATE-04, FR-DIR-05                |
| A-08 the built-in personal agent is enough at launch        | FR-APP-03                                          |

## 5. User stories for the next phases

### Phase 2

**FR-GATE-01, FR-GATE-02.** As Dana, I want to approve one specific offer, so that my agent can never book something I didn't see.

- **Given** my agent received a valid offer for a haircut on Thursday at 17:30 for 30.00 USD, **when** I approve it, **then** my agent sends a `booking_request` for that `offerId` only, and the approval is recorded in my audit log.
- **Given** I approved offer A, **when** any code tries to book offer B with that approval, **then** it is refused and nothing is sent.
- **Given** the offer is within P-09 of its deadline or past it, **when** I approve it, **then** my agent tells me it expired and asks the barber agent for a fresh offer.

**FR-BOOK-01, FR-BOOK-02, FR-BOOK-07.** As Marcus, I want offers to hold the slot briefly and bookings to be decided once, so that two customers are never given the same chair.

- **Given** the barber agent offered 17:30 to Dana, **when** another agent asks for the same window before the offer expires, **then** 17:30 is not offered.
- **Given** a `booking_request` with an unknown, expired or other-context `offerId`, **when** it arrives, **then** the barber agent answers `booking_rejected` (`unknown_offer` or `expired`) and its book is unchanged.
- **Given** two `booking_request`s for the same slot arrive together, **when** both are processed, **then** exactly one is confirmed.
- **Given** Dana's agent retries the same `booking_request`, **when** it arrives, **then** it gets the same Task back, not a second booking.

**FR-GATE-05.** As Marcus, I want to approve bookings myself on busy days, so that I stay in control of my chair.

- **Given** my shop is set to manual approval, **when** Dana's agent sends a `booking_request`, **then** the offer becomes Reserved, the Task stays WORKING with "waiting for the shop", and Dana's agent polls for the result.
- **Given** I don't answer within P-03, **when** the time passes, **then** the Task ends `booking_rejected` with `shop_timeout` and the slot is free again.

**FR-BOOK-08, FR-BOOK-09.** As Marcus, I don't want strangers to lock up my chairs with offers they never take.

- **Given** Dana declines an offer, **when** her agent sends `offer_declined`, **then** the slot is offered again at once.
- **Given** one sender already has P-07 open holds, **when** it asks again, **then** it gets `rejected` and no new hold.

**FR-GATE-03, FR-MSG-11.** As Dana or Marcus, I want a record of what my agent proposed and what was decided, so that I can check what happened if something goes wrong.

- **Given** a completed booking, **when** I read my audit log, **then** it shows the offer, my decision with a timestamp, the booking request and the result, in order, each with the shared `contextId`, `taskId`, `offerId` and `messageId`, with no entries changed or removed.

**FR-BOOK-03, FR-BOOK-10, FR-BOOK-11.** As Dana, I want to cancel or move my booking through my agent, so that I don't have to call the shop.

- **Given** a confirmed booking, **when** I cancel it, **then** the barber's book frees the slot, both audit logs record the cancellation, and the slot can be offered again.
- **Given** the shop has a cutoff and I'm inside it, **when** I cancel, **then** the Task ends REJECTED with `cancel_rejected` reason `cutoff` and my booking stands.
- **Given** I reschedule and the new slot is taken before I approve, **when** the booking fails, **then** my original booking is unchanged.

### Phase 3

**FR-DIR-01.** As Marcus, I want to list my shop's agent, so that customers' agents can find me.

- **Given** I submit my agent card URL and place the verification token on that origin (or its DNS), **when** verification runs, **then** the listing goes live marked as verified.
- **Given** I can't prove control, **when** I submit, **then** the listing is not published.

**FR-DIR-02.** As Dana, I want to find a barber near me who does fades, so that my agent can ask them for a slot.

- **Given** listings exist, **when** I search for "fade" near my area, **then** I get matching verified listings with their agent card links, nearest first.

**FR-DIR-03.** As Dana, I want my agent to talk only to the business I picked, so that a listing can't redirect me somewhere else.

- **Given** a listing at `https://shop.example`, **when** its card's interface URL points at another origin, **then** my agent refuses to send it anything and the directory flags the listing.
