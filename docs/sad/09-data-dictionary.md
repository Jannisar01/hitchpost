## 1. Purpose and scope

This is the authoritative definition of every data element in Hitchpost: entities from the domain model in [08 Data design](08-data-design.md) and [22 Enhanced entity relationship model](22-enhanced-entity-relationship-model.md), and fields of the agent message contract in [13 Interfaces](13-interfaces.md). Where a field is Built, its type and limits here match `packages/core/src/booking.ts` exactly; if the two ever disagree, the code is the defect and this dictionary is the specification. Hitchpost is a network of agent lines between users, person to person and person to business; the booking fields are worked out in the most detail because barbers are the first vertical.

## 2. Naming conventions

| Rule                                                                                                                | Example                                             |
| ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| Fields are `camelCase` on the wire and in TypeScript; `snake_case` in SQL columns                                   | `durationMinutes` / `duration_minutes`              |
| Message `kind` values and enumerations are `snake_case` strings                                                     | `availability_request`, `slot_taken`                |
| Units go in the name, never implied                                                                                 | `durationMinutes`, `priceCents`, `latencyMs`        |
| Instants on the wire are ISO 8601 UTC strings; stored instants end in `Ms` (SQLite) or are `timestamptz` (Postgres) | `start` / `start_ms`, `expiresAt` / `expires_at_ms` |
| Identifiers end in `Id` and are opaque strings; nobody parses meaning out of them                                   | `offerId`, `bookingId`, `serviceId`                 |
| Money is an integer number of minor units plus an ISO 4217 code; never a float                                      | `priceCents: 3000`, `currency: "USD"`               |
| Entities are singular nouns (`Booking`); stores and tables are plural (`bookings`)                                  |                                                     |

## 4. Message contract elements

All messages travel as A2A data parts with `mediaType: application/json` and a required `kind`. Unknown fields are dropped on receipt (FR-MSG-03). A receiver answers an unknown request `kind` with `rejected` reason `unsupported_kind`; a new reply kind is only sent to a client that advertised support for it, and a client that still meets one reports "unsupported reply" instead of failing.

### 4.4 Phase 2 and later kinds

Authority comes from server-minted secrets, not from `contextId`, which the client chooses (SDK `server/index.js:2815`): `offerId` authorises acting on an offer, `bookingToken` authorises acting on a booking. Until agent authentication (Phase 6) both are bearer capabilities (see [12](12-security-and-privacy.md)). Clients send the contract extension uri `https://hitchpost.dev/ext/contract/v1` in the `A2A-Extensions` header, which is where the SDK checks it (`server/index.js:2775-2781`), and also list it in each message's `extensions`.

## 8. Data quality rules

Dimensions from ISO/IEC 25012.

| ID    | Dimension    | Rule                                                                                                                                                         | Check                                                               | Status                                    |
| ----- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------- | ----------------------------------------- |
| DQ-01 | Accuracy     | Every instant is stored as canonical UTC with an explicit zone on input                                                                                      | `toInstant`; unit tests                                             | Built                                     |
| DQ-02 | Consistency  | No two bookings in one business overlap                                                                                                                      | `findFreeSlot`; Phase 6 database exclusion constraint               | Built (search)                            |
| DQ-03 | Consistency  | `booking_confirmed` equals the approved offer field for field                                                                                                | Personal agent field check (Phase 2); also gates the calendar write | Phase 2 (check), Phase 4 (calendar write) |
| DQ-04 | Completeness | Every booking has an offer, an approval and audit events on both sides, joined on `offerId` and `bookingId` (never on `contextId`, which the client chooses) | Audit reconciliation job                                            | Phase 2                                   |
| DQ-05 | Validity     | Every inbound field passes its §3 type rule                                                                                                                  | Parsers in `booking.ts`                                             | Built                                     |
| DQ-06 | Currentness  | Expired, declined and released offers never block slots; open holds capped (P-07)                                                                            | Slot search ignores them; offer store counts holds                  | Phase 2                                   |
| DQ-07 | Credibility  | Only verified listings are searchable; only two-sided interactions are rated                                                                                 | Directory and rating ingest                                         | Phase 3, 5                                |
| DQ-08 | Traceability | Each booking can be followed end to end by `contextId`, `taskId`, `offerId`, `bookingId` and `messageId`                                                     | Audit reconciliation; trace ids added in Phase 6                    | Phase 2 (ids), Phase 6 (traces)           |
| DQ-09 | Completeness | Every past booking gets an outcome or becomes `unresolved` at P-25; the unmarked rate is reported weekly                                                     | Outcome resolver job; counter-metric                                | Phase 4                                   |
| DQ-10 | Validity     | Test bookings (test businesses, canary) never reach analytics or the north star                                                                              | `isTest` flag on the business; excluded at ingest                   | Phase 4                                   |
| DQ-11 | Validity     | No `bookingToken` or other capability appears in plain text in any store or the SDK task history                                                             | Test scans `a2a_tasks.history` and logs after every e2e run         | Phase 2                                   |
| DQ-12 | Consistency  | Stored timestamps have one canonical form                                                                                                                    | SQLite INTEGER epoch ms with CHECK; Postgres `timestamptz`          | Phase 2                                   |
