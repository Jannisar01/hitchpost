## 1. Purpose and scope

This is the project test plan for Hitchpost from Phase 1 to v1 (end of Phase 6), in the structure of ISO/IEC/IEEE 29119-3. It covers the test items, the features in and out of scope, the risks that drive test priority, the approach per level, a catalogue of test cases with stable IDs (`TC-nn`), entry, exit, suspension and resumption criteria, environments and deliverables. Requirements trace to these test cases in the [traceability matrix in 05](05-requirements.md#7-traceability-matrix); every FR and NFR there names its verification method and test cases. The step-level test case specification and the UAT scripts are in [34 Functional test specification](34-functional-test-specification.md); this plan owns the IDs and the approach, 34 owns the steps.

The pilot runs with standing approval only; business-side manual approval is Later and is not tested until it is built.

References: [05 Requirements](05-requirements.md), [11 Quality attributes](11-quality-attributes.md), [12 Security and privacy](12-security-and-privacy.md), [18 Deployment and operations](18-deployment-and-operations.md), [01 v1 release criteria](01-vision-and-scope.md#8-v1-release-criteria-end-of-phase-6), parameter register in [00](00-document-control.md#10-normative-parameters-and-phase-map).

## 2. Test policy: test first

**Test first for every bug and every trust-boundary rule.** Write the failing test, watch it fail, then fix.

The [Phase 1 audit](../audits/2026-11-08-phase-1.md) is why. Lint, types and 11 tests were all green while five real bugs got through, because the tests only checked the happy path. The fixes all landed test-first, and the auditors' attacks were re-run against the fixed code. The audit also caught one wrong _test_ (a 60-minute service expected past closing time), so tests get reviewed like code. The expert panel audit found one more real hole the same way: the client followed a card's call address to another origin. TC-23 failed first, then the fix landed (commit 047edef).

## 4. Features to be tested and not tested

**Tested:** every FR and NFR in [05](05-requirements.md), each through the method and test cases its traceability row names.

**Not tested, with the reason:**

| Feature                                                      | Why not                                                                                                             |

| The A2A SDK's own transports beyond JSON-RPC (REST, gRPC)    | Not advertised in our agent cards until tested; NFR-INT-01 covers what we advertise.                                |

## 5. Risk basis

Test priority follows product risk (R- in [03](03-business-case.md)) and security threats (T- in [12](12-security-and-privacy.md)). High-risk areas get tests at more than one level.

| Risk or threat         | What could go wrong                                             | Test response                                                                                                  | Priority            |
| ---------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------- |
| R-04, T-01, T-02, T-11 | Hostile or malformed input crashes an agent or reaches a person | Validator tables, property tests, injection corpus, hostile-agent fixtures (TC-13, TC-15, TC-20, TC-49, TC-50) | High                |
| T-03, R-07             | A wrong offer is shown for approval                             | Offer matching unit and end-to-end (TC-16, TC-21)                                                              | High                |
| T-04, T-10             | A booking without approval, or approval of A books B            | Gate, binding and capability-token tests including a type-level fixture (TC-42, TC-43, TC-48)                  | High                |
| R-07, NFR-REL-02       | Double booking or a lost booking                                | Concurrency race, idempotent retry, restart survival, restore drill (TC-35, TC-36, TC-46, TC-59, TC-100)       | High                |
| T-05, T-06, R-06       | One sender exhausts CPU or chairs                               | Window cap, install-key caps, rate limits, de-duplication (TC-13, TC-38, TC-47, TC-54, TC-93)                  | Medium              |
| T-08                   | Error responses leak internals                                  | Error-path probe (TC-30)                                                                                       | Medium              |
| T-12, T-13             | Client hangs or is steered to another host                      | Deadline and origin tests (TC-22, TC-23 Built; TC-56, TC-62)                                                   | Medium              |
| R-05, T-07, T-15       | Fake business agents                                            | Verification from Phase 3 (TC-60); signed cards from Phase 6 (TC-92)                                           | High from Phase 3   |
| T-16                   | Fake reviews                                                    | Rating eligibility (TC-80)                                                                                     | Medium from Phase 5 |
| R-08                   | Personal data exposure or kept too long                         | Contact block scoping (TC-53); export and delete (TC-97)                                                       | High                |
| R-10                   | A2A changes break interop                                       | Conformance kit, third-party agent and contract fixtures per version (TC-31, TC-57, TC-64)                     | Medium              |

## 9. Test data, environments and time

- **Fixed clocks.** Anything that depends on "now" takes it as a parameter (`findFreeSlot(..., now)`, `new BarberExecutor(book, now)`). Tests pin it to 2026-11-01 so they never rot as dates pass.
- **Injectable scheduler and fake timers (Phase 2).** Phase 2 waits are long (P-01 is 10 minutes). Every timer in our code (holds, expiry sweeps, retries, deadlines) goes through an injectable scheduler, and tests drive it with `node:test` `mock.timers`, so TC-33, TC-36 and TC-43 run in milliseconds and never sleep. SDK internals that use the real clock are only exercised through short, explicit deadlines. TC-22 moves onto this in Phase 2.
- **Known calendar.** 2026-11-12 is a Thursday; the test book is open Thursdays 9 to 18 UTC.
- **Free ports.** Servers bind `127.0.0.1` on port 0, so tests run in parallel and in CI without clashes.
- **Hostile agents are test fixtures.** `SneakyExecutor` in `ask.test.ts` is a subclass of the real executor, so it stays a valid A2A agent with only the lie changed; TC-23 serves a real card from a decoy origin.
- **Named injection corpus** for TC-50, pinned by version (section 7.2).
- **No real personal data** in any environment before Phase 6; pilot data follows [12](12-security-and-privacy.md) retention. Canary and test bookings are tagged and excluded from product metrics.

**SDK-upgrade regression suite.** Any change to the `@a2a-js/sdk` version runs, in its own PR: the full e2e and contract suites, the conformance kit, and the behaviour tests the design depends on (TC-36 duplicate handling, TC-48 client-chosen `contextId`, TC-51 extension header). These test the SDK behaviour itself, so a patch release that moves code around can't silently change it; the SDK source line numbers cited in [13](13-interfaces.md) and ADR 0012 are re-checked in the same PR.

## 10. Suspension and resumption

| Suspend when                                                           | Resume when                                                                              |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| CI is red on `main`                                                    | The breaking change is reverted or fixed; CI green on `main`                             |
| An end-to-end test fails intermittently                                | Quarantine policy below; root cause found and fixed; the test passes three runs in a row |
| A high or critical security finding is open on the item under test     | The fix is merged with a test that failed before it                                      |
| Staging is down or diverges from the release commit                    | Staging redeployed from the release tag and smoke test green                             |
| A pilot SEV1 per [19](19-maintenance-and-evolution.md#1-support-model) | Rollback done, root cause fixed, go/no-go re-run                                         |

**Flaky test quarantine.** A test that fails and then passes on retry with no code change is tagged `flaky`, logged as an issue and moved to a quarantine list that still runs but doesn't gate; it must be fixed or deleted within 5 working days. Gate-critical tests can never be quarantined: TC-35, TC-36, TC-42, TC-43, TC-46, TC-48 and TC-100. If one of those flakes, the suite is suspended until it's fixed.

## 12. CI gates

Every PR and every push to `main` runs, in order (`.github/workflows/ci.yml`):

1. `pnpm install --frozen-lockfile`
2. `pnpm check` (Biome lint and format)
3. `pnpm typecheck` (tsc, including `erasableSyntaxOnly`)
4. `pnpm test` (including the property tests and coverage from Phase 2)
5. `pnpm docs:check` (document consistency)

All five run in the required check `lint, typecheck, test`. From Phase 2 (WP-2.17), CodeQL and secret scanning run as separate required checks on every PR; the mutation job runs on a monthly schedule and on every release tag. The AI-assisted review is advisory.

## 13. Mutation testing and coverage

The QA auditor mutated the code by hand and found 9 changes the old tests didn't notice. To keep that from happening again, Stryker runs on `packages/core` and `findFreeSlot` in a CI job, monthly and on every release tag. Target: a mutation score of at least 80% on the validators and `findFreeSlot`. "No surviving mutants" is not used, because equivalent mutants make it impossible; each surviving mutant is either killed with a test or recorded as equivalent in the report. Coverage is measured with `node --experimental-test-coverage` on every CI run; line coverage of `packages/core` stays at or above 90%.
